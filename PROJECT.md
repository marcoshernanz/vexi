# Vexi - DX-First RAG Database

Vexi is a developer-experience-first database for RAG apps: you define tables in TypeScript (in `schema.ts`) with a Zod-like API, run `npx vexi sync` to migrate/sync the schema, and then use a fully type-safe TypeScript client to `insert`, `update`, and `search`.

The backend is a Rust server (Axum) that owns storage + embedding generation. Developers should never have to manually call an embeddings API or manage vector columns.

## The Core Promise

- Zod-like schema builder API (ergonomic, chainable, familiar).
- End-to-end type safety: the same schema definition drives client-side types and server-side validation.
- One-command schema sync/migrations: `npx vexi sync`.
- Automatic embeddings on write and on query.
- Embeddings provider: Gemini only (v1).

## Developer Workflow

1. Define tables in `schema.ts`.
2. Run `npx vexi sync`.
3. Use the SDK:
   - `db.<table>.insert(...)`
   - `db.<table>.update(...)`
   - `db.<table>.search(...)`

## Schema API (Zod-Like)

Goal: feel as close to Zod as possible, while still being a database schema definition.

Example shape (illustrative):

```ts
// schema.ts
import { createTable, v } from "vexi";

export const users = createTable({
  name: v.string().embed(),
  bio: v.optional(
    v.string().embed({
      model: "models/text-embedding-004",
      strategy: "recursive-markdown",
    }),
  ),
  isActive: v.boolean(),
});
```

Notes:

- `createTable(...)` is the canonical table constructor.
- Optionality follows Zod's wrapper style: `v.optional(v.string())`.
- `v.*` should be chainable and predictable (like `z.*`).
- The schema must be serializable into a stable, backend-consumable format (an AST/JSON schema), so the Rust server can validate writes and run migrations.

## Defaults / Decisions (v1)

- Primary key: every table has an implicit `id: string` primary key generated by the server (you don't declare it in `schema.ts`).
- Embedded fields: multiple fields can opt into `.embed()`. Vexi builds a single canonical per-row `vector` by concatenating the embedded field contents in a stable, labeled format and embedding that combined text.
- Search return type: `search(...)` returns scored results: `Array<{ item: Row; score: number }>`.

Implementation note:

- The SDK's type surface reflects these v1 decisions even if early backend endpoints temporarily return simpler payloads while milestones are in progress.

If chunking is enabled (e.g. `strategy: "recursive-markdown"`), the server maintains an internal chunk index and maps chunk hits back to the parent rows.

## Tables, Migrations, and Sync

`npx vexi sync`:

- Loads `schema.ts` from the project root.
- Extracts exported tables.
- Sends schema definitions to the Rust API.
- The API stores schema + migration metadata and applies non-destructive changes automatically (add columns, add indexes, etc.).

Destructive or ambiguous migrations (changing types, removing columns, changing embedding config that implies re-embedding) should be explicit and safe by default.

## SDK (TypeScript)

The SDK provides:

- Schema DSL (`createTable`, `v.*`).
- `createClient({ schema, config })` that returns a typed client, ideally accessed as `db.users.insert(...)` with autocomplete.
- End-to-end inference: `insert/update/search` input and output types derive from `schema.ts`.

The client should be a thin transport + types layer. It should not need to know how to embed.

## Backend (Rust)

The Rust API server:

- Owns persistence (currently LanceDB is used in this repo).
- Owns schema registry (what schema is active, how it evolved).
- Validates incoming writes against the active schema.
- Automatically generates embeddings on insert/update for configured fields.
- Automatically embeds search queries and runs vector search.

## Automatic Embeddings

Intended behavior:

- When a table has one or more embedded fields, the server computes embeddings during `insert`/`update` and stores vectors.
- When the developer calls `search("...")`, the server embeds the query (same provider/model) and runs similarity search.
- Chunking/splitting strategies (e.g. `recursive-markdown`) should be supported server-side so the client stays simple.

## Embeddings

v1 uses Gemini embeddings only.

Provider/model selection is primarily server-configured (env/config). The schema can optionally specify a `model` hint per embedded field (e.g. `models/text-embedding-004`) for portability and to make intent explicit.

## What "E2E Type Safety" Means Here

- The schema defines runtime validation rules (server) and compile-time types (client).
- If schema changes, `sync` updates server-side validation and client types update automatically via TypeScript inference.
- The server should reject invalid writes even if a client bypasses TypeScript.

## Remaining Design Space

- Filters/hybrid search: likely `search(query, { topK, where, mode })` where `where` is a typed filter over non-vector fields, and `mode` can evolve from `"vector"` to `"hybrid"`.
- Multi-vector / per-field search: possible later (e.g. `search(query, { field: "bio" })`), but v1 keeps a single canonical `vector` per row for simplicity.
